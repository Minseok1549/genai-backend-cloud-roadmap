이 문서를 읽는 법

여기 나오는 개념은 전부 이 프로젝트(genai-backend-cloud-roadmap)를 만드는 과정에서 실제로 필요했던 것들이다. 교과서처럼 순서대로 다 외울 필요는 없고, 다음에 비슷한 서비스를 만들 때 "이건 저번에 어떻게 했더라" 싶은 순간 이 페이지로 돌아와 해당 장만 다시 읽으면 된다.

각 장은 세 가지를 항상 같이 말한다 — 이게 왜 필요한가(문제 상황), 이 프로젝트에서 어떻게 썼는가(실제 코드), 다른 클라우드에서는 뭐라고 부르는가(벤더 중립 대응표). 마지막 항목을 넣은 이유는, "배포해봤다"와 "이해했다"는 다르기 때문이다 — 특정 클라우드의 명령어를 외우는 것과, 그 명령어가 풀고 있는 일반적인 문제를 아는 것은 별개의 능력이다.

01

API 서버의 뼈대 — FastAPI 레이어

백엔드 서버가 하는 일은 결국 "요청을 받아서 뭔가 하고 응답한다"인데, 그 사이에 끼워야 하는 것들이 있다. 이 프로젝트의 /predict 엔드포인트 하나에 그게 다 들어있다.

검증
Pydantic 모델로 요청 본문의 타입·길이를 서버 로직 진입 전에 걸러낸다. 홈팀/원정팀 이름이 비어있거나 너무 길면 여기서 400으로 끝난다 — 그 뒤 코드는 "값이 정상"이라는 전제를 믿고 짤 수 있다.
수명주기
lifespan 이벤트로 서버가 뜰 때 모델 파일과 DB 커넥션 풀을 한 번만 준비한다. 요청마다 모델을 다시 읽으면 느리고, 아예 안 읽어놓으면 첫 요청에서야 실패를 발견한다.
부분 장애
DB가 죽어 있어도 서버 전체가 죽으면 안 된다. 예측 응답은 그대로 내려주고, 기록 저장만 실패로 로그를 남긴다 — 부가 기능(감사 기록)과 핵심 기능(예측)의 장애를 분리하는 것이 이 판단의 기준이다.
# lifespan: 기동 시점에 한 번, 실패하면 바로 죽는 것과 조용히 넘어가는 것을 구분한다
app.state.model_bundle = load_model_bundle(MODEL_PATH)  # 없으면 기동 자체를 실패시킨다

try:
    app.state.db_pool = db.create_pool()
except Exception:
    app.state.db_pool = None  # DB 없이도 /health, /predict는 계속 서빙

미들웨어에서는 요청마다 X-Request-ID를 붙이고 응답 시간을 구조화 로그로 남긴다. 이건 06장(로깅)에서 더 자세히 다룬다.

02

외부 API는 반드시 캐싱한다

이 서비스는 football-data.org라는 외부 API에서 경기 데이터를 받아온다. 무료 티어는 분당 호출 횟수 제한이 있어서, 요청이 들어올 때마다 외부 API를 부르면 금방 막힌다. 그래서 로컬 JSON 파일에 캐싱하고, 완결된 시즌은 영원히 안 바뀌니 한 번만 받고, 진행 중인 시즌만 일정 시간(6시간)마다 다시 받는다 — 데이터의 성격에 따라 캐시 정책을 다르게 가져가는 것이 핵심이다.

실전에서 배운 것

캐시 파일을 쓰는 도중에 다른 요청이 그 파일을 읽으면 깨진 JSON을 보게 된다. 그래서 임시 파일에 먼저 쓰고 os.replace()로 원자적으로 교체한다 — 운영체제 수준에서 "전부 바뀌거나 전혀 안 바뀌거나" 둘 중 하나만 보이게 보장해주는 연산이라, 절반만 쓰인 파일을 읽는 경우가 없다.

tmp_path.write_text(json.dumps(data))
os.replace(tmp_path, out_path)  # 두 줄이지만, 동시성 버그를 막는 핵심

그리고 받아온 응답을 캐시에 쓰기 전에 스키마를 검증한다(점수 필드가 있는지, winner 값이 정상 범위인지). 검증에서 걸리면 기존 캐시를 그대로 두고 실패시킨다 — 손상된 데이터가 캐시에 들어가면, 그걸 읽는 모든 이후 요청이 이유도 모른 채 500 에러를 내기 때문이다.

03

배치와 서비스는 다른 세계에 산다

이 프로젝트에서 가장 비직관적이었던 함정이다. "매일 예측을 계산하는 배치 작업"과 "사용자 요청을 받는 API 서버"를 같은 코드베이스, 같은 컨테이너 이미지로 만들어도, Cloud Run Job과 Cloud Run Service는 완전히 별개의 컨테이너 인스턴스로 뜬다. 배치가 로컬 디스크에 써놓은 캐시 파일은 서비스 컨테이너에서 절대 보이지 않는다 — 디스크를 공유하지 않기 때문이다.

실제로 겪은 버그

대시보드가 종료된 경기의 스코어를 안 보여주는 문제가 있었다. 원인은 대시보드 라우트가 로컬 캐시 파일을 읽기만 하고 갱신은 /predict 라우트에서만 트리거됐던 것 — 아무도 /predict를 안 부르면 서비스 컨테이너의 캐시는 기동 시점에 멈춰 있었다. 고친 방법은 대시보드 라우트에도 같은 캐시 갱신 호출을 추가한 것이다. "배치가 데이터를 갱신했으니 서비스도 알겠지"는 서로 다른 컨테이너 사이에서는 틀린 가정이다.

04

여러 컨테이너가 공유할 진실은 객체 스토리지에

배치와 서비스가 디스크를 공유하지 않는다면, 배치가 계산한 결과(그날의 예측)를 서비스가 어떻게 읽을까? 답은 둘 다 접근 가능한 외부 저장소다. 이 프로젝트는 배치가 매일 계산한 예측을 GCS(객체 스토리지)에 predictions/{날짜}.json으로 올리고, 서비스는 요청이 올 때마다 그 파일을 읽는다.

여기서 얻은 원칙: 인스턴스 로컬 디스크는 "이번 실행에서만 쓰는 임시 작업 공간"으로만 쓰고, 다음에 누군가(다른 실행, 다른 서비스)가 읽어야 하는 값은 반드시 로컬 밖으로 내보낸다. 이건 Cloud Run뿐 아니라 컨테이너 기반 아키텍처 전반에 적용되는 규칙이다.

05

DB는 선택적 의존성으로 다룬다

Postgres에 psycopg2로 접속해서 예측 기록(감사 추적용)을 남긴다. 커넥션은 매번 새로 열지 않고 커넥션 풀을 기동 시점에 하나 만들어 재사용한다 — 매 요청마다 TCP 연결을 새로 맺는 비용을 없애기 위해서다.

중요한 설계 판단은 01장에서 이미 나왔다: DB는 예측 기능의 필수 조건이 아니라 부가 기록 기능의 필수 조건이다. 그래서 기동 시점 DB 연결 실패, 요청 처리 중 저장 실패 모두 로그만 남기고 예측 응답 자체는 정상적으로 내려준다. "이 의존성이 없으면 무엇까지 포기해도 되는가"를 먼저 정하고 코드를 짜는 순서가 반대로 되면, 사소한 부가 기능 장애가 핵심 기능까지 끌고 내려가는 설계가 나온다.

06

로그는 기계가 먼저 읽는다 — 구조화 로깅

사람이 눈으로 훑는 텍스트 로그 대신, JSON 한 줄에 필드를 담아 남긴다(log_json("warning", "메시지", fixture_id=..., error=...) 형태). 이렇게 하면 나중에 "왜 이 세 경기만 예측이 빠졌지?"를 조사할 때, 로그 검색 도구에서 jsonPayload.message="daily prediction skipped for fixture"처럼 필드 기준으로 정확히 걸러낼 수 있다. 실제로 이 방식 덕분에 대시보드에서 3경기가 빠진 원인(폼 기록 부족으로 모델이 건너뜀)을 로그 검색 한 번으로 찾아냈다.

미들웨어에서 요청마다 X-Request-ID를 발급하고 모든 로그 줄에 함께 남기는 것도 같은 이유다 — 요청 하나가 여러 로그 줄을 남길 때, 그 줄들을 하나로 묶어 추적하려면 공통 식별자가 있어야 한다.

07

배포는 "이미지 하나를 새로 쌓는" 일이다

gcloud run deploy --source . 한 번이 하는 일: 소스 코드를 컨테이너 이미지로 빌드 → 그 이미지를 Artifact Registry(이미지 저장소)에 올림 → 새 리비전을 만들어 트래픽을 그쪽으로 전환. 여기서 놓치기 쉬운 것: 배포할 때마다 이전 이미지가 저장소에서 자동으로 지워지지 않는다. 배포를 반복할수록 다이제스트(이미지 버전)가 계속 쌓이고, 스토리지 비용도 함께 늘어난다.

이 프로젝트의 규칙

배포 후에는 항상 현재 실제로 트래픽을 받는 리비전의 이미지 다이제스트를 먼저 확인하고(gcloud run revisions describe ... --format="value(spec.containers[0].image)"), 그 다이제스트를 제외한 나머지를 지운다. 순서를 바꿔서 확인 없이 지우면, 서비스 중인 이미지를 실수로 지울 수 있다.

gcloud run revisions describe <revision> --region=... \
  --format="value(spec.containers[0].image)"   # 1. 지금 쓰는 다이제스트 확인

gcloud artifacts docker images delete <image>@<다른 다이제스트> \
  --quiet --delete-tags                         # 2. 확인 후에만 나머지 삭제
역할GCPAWSAzure
버전 단위 배포 이력Revision (Cloud Run)Task Definition Revision (ECS)Revision (Container Apps)
08

비밀값은 코드가 아니라 환경이 쥔다

API 키, DB 비밀번호 같은 값은 코드에 절대 하드코딩하지 않는다. 이 프로젝트의 규칙: 운영 환경(Cloud Run)에서는 환경변수로 주입받고, 로컬 개발에서만 .env 파일을 fallback으로 읽는다. .env는 .gitignore에 반드시 포함시켜 git 이력에 절대 들어가지 않게 한다.

env_key = os.environ.get("FOOTBALL_DATA_API_KEY")
if env_key:
    return env_key
# 배포 환경엔 .env가 없으니, 여기 도달하면 로컬 개발 중이라는 뜻

다음 장에서 다룰 Gen AI API 키(Gemini)도 같은 규칙을 그대로 따른다 — Cloud Run 서비스의 환경변수(또는 Secret Manager)로 등록하고, 로그에는 절대 값 자체를 남기지 않는다.

09

MLOps의 최소 단위 — 버전, 멱등성, 격리

"MLOps"라고 하면 거창하게 들리지만, 이 프로젝트에서 실제로 지킨 건 네 가지 습관뿐이다.

모델·데이터 버전 기록

감사 추적

예측 결과마다 model_version(어느 모델로 계산했는지)과 data_version(어느 시점까지의 경기 데이터를 반영했는지)을 함께 저장한다. 나중에 "이 예측이 왜 이렇게 나왔지?"를 재현하려면, 결과값뿐 아니라 그걸 만든 조건도 같이 남아있어야 한다.

실패 하나가 배치 전체를 막지 않는다

격리

승격팀처럼 폼 기록이 부족한 경기 하나가 예측에 실패해도, 그 경기만 건너뛰고 나머지 경기 예측은 계속 진행한다. 배치 작업에서 "부분 실패"와 "전체 실패"를 구분하지 않으면, 경기 하나의 데이터 결함이 그날 전체 대시보드를 텅 비게 만든다.

같은 배치를 다시 돌려도 안전하게(멱등성)

재실행 안전

배치가 오전, 오후 두 번 돌아도 오전에 기록한 예측이 사라지면 안 된다. 그래서 새 결과와 기존 저장값을 match_id 기준으로 병합하고, 겹치는 경기만 새 값으로 덮어쓴다 — 재실행이 데이터를 망가뜨리지 않는다는 것을 보장하는 가장 기본적인 패턴이다.

외부 의존성은 테스트에서 가짜로 바꾼다

결정론적 테스트

GCS, DB, 실제 모델 파일을 실제로 부르면 테스트가 느리고 네트워크에 따라 결과가 흔들린다. monkeypatch로 이런 외부 호출을 가짜 함수로 바꿔치기해서, "이 로직이 이 입력에서 이 출력을 내는가"만 빠르고 항상 같은 결과로 검증한다.

10

다음 레이어 — Gen AI를 어디에 끼울 것인가

대시보드에 경기별 프리뷰(선수 현황, 상대 전적, 이슈 요약)를 Gen AI로 붙이기로 했다. 여기서도 위에서 배운 원칙이 그대로 적용된다: LLM 호출은 비용이 실제로 드는 외부 API 호출이므로, 캐싱 원칙(02장)과 배치/서비스 분리 원칙(03장)을 그대로 가져온다.

채택 안 함
실시간 생성 — 사용자가 대시보드를 열 때마다 LLM을 호출하면, 트래픽만큼 비용이 늘고 페이지 로딩도 느려진다.
채택함
배치 생성 + 캐시 서빙 — 하루 배치 작업이 그날 대상 경기마다 딱 한 번씩 LLM을 호출해 결과를 GCS에 저장한다(04장의 "진실 원천" 패턴 재사용). 대시보드는 그 결과를 읽기만 하므로 비용이 "경기 수 × 1회"로 고정되고 예측 가능하다.

모델은 비용 때문에 Gemini로 정했다. 어떤 LLM을 쓰든 이 배치-생성/캐시-서빙 구조 자체는 바뀌지 않는다 — API 키만 바뀔 뿐이고, 그 키를 다루는 규칙은 08장과 동일하다.

✓

다음 Gen AI 프로젝트에 그대로 옮길 체크리스트

  • 외부 API를 부르는 곳마다: 캐시가 있는가, TTL이 데이터 성격에 맞는가, 쓰기가 원자적인가
  • 배치(Job)와 서비스(Service)가 나뉘어 있다면: 배치가 만든 결과를 서비스가 읽는 경로가 로컬 디스크가 아니라 객체 스토리지인가
  • 핵심 기능과 부가 기능(로깅, 기록 저장 등)의 장애를 분리했는가 — 부가 기능이 죽어도 핵심은 응답하는가
  • 로그가 사람이 눈으로 읽는 텍스트가 아니라, 필드로 검색 가능한 구조화 로그인가
  • 배포 후 이전 컨테이너 이미지를 정리하는 습관이 있는가(현재 사용 중인 다이제스트 확인 → 나머지 삭제)
  • 비밀값이 코드나 git 이력이 아니라 환경변수/Secret Manager에만 있는가
  • 배치를 다시 돌려도 기존 데이터가 유실되지 않는가(멱등적 병합)
  • LLM 호출처럼 비용이 실제로 드는 작업은, 요청마다가 아니라 배치로 한 번만 계산하고 캐시로 서빙하는가
  • 테스트가 외부 의존성(DB, 스토리지, 실제 모델) 없이도 결정론적으로 돌아가는가
