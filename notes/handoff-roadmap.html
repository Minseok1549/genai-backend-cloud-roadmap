지금 상태 — 완전한 백지

2026-08-31에 시작한 8주짜리 백엔드~클라우드 로드맵과 그 실습 코드(pl-match-predictor/, genai-backend-cloud-roadmap/)를 2026-09-05에 전부 삭제했다. Git 이력이 없었기 때문에 복구 불가능한 삭제였고, 여기에는 원래 있던 EPL 예측 모델 코드(features.py, train.py)까지 포함된다.

주의해야 할 것

목표도 함께 바뀌었다. 원래는 8주에 걸쳐 개념을 깊이 이해하는 것이었다면, 지금은 이해의 깊이보다 위임의 정확도를 기른다. 코드는 Claude Code가 짜고, 사용자는 무엇을 어떤 형식으로 요청해야 좋은 결과가 나오는지를 이 이틀 동안 반복 훈련한다.

01

왜 "위임하는 법"이 따로 배울 일이 됐나

2025년 초 Andrej Karpathy가 만든 "vibe coding"이라는 말은 원래 "설명하고, 받아들이고, 넘어간다"는 가벼운 작업 방식을 가리켰다. 그런데 2026년 그가 직접 이 방식의 종료를 선언했다. Sequoia AI Ascent 발표에서 그는 "vibe coding은 바닥을 높였을 뿐이고, 지금 필요한 건 천장을 넓히는 것"이라며 후속 개념으로 agentic engineering을 제시했다.

Vibe CodingAgentic Engineering
사람의 역할요청하고 결과를 수용스펙 설계, 계획 감독, 권한 관리
검증돌아가면 끝diff 검사, 테스트, 평가 루프를 직접 설계
격리메인 브랜치에 바로 반영worktree/브랜치로 격리 후 병합
실패 원인AI가 틀렸다내 스펙이 모호했다

이 표의 오른쪽 칸이 이번 이틀 동안 사용자가 실제로 연습할 역할이다. 코드를 직접 짜지 않아도, "오케스트레이터"로서 해야 할 일은 분명히 있다.

02

스펙 기반 위임 프레임워크

GitHub가 만든 오픈소스 도구 Spec Kit은 "무엇을 어떻게 시켜야 하는가"를 4단계로 표준화했다. 이번 스프린트의 모든 블록은 이 순서를 따른다.

1 Specify
무엇을, 왜
기술 디테일 없이 요구사항과 이유만
2 Plan
어떻게
스택, 아키텍처, 제약 조건
3 Tasks
작은 단위로
독립적으로 테스트 가능한 작업 목록
4 Implement
구현
작은 diff, 각 단계 검증 후 다음 단계

핵심 규칙은 하나다 — 현재 단계가 완전히 검증되기 전에는 다음 단계로 넘어가지 않는다. 스펙이 애매하면 AI가 마음대로 해석하게 두지 말고 [NEEDS CLARIFICATION]처럼 표시하게 시킨다.

스펙에 반드시 넣을 6가지

Addy Osmani가 2,500개 이상의 실제 agent 설정 파일을 분석해 정리한 항목이다. 길게 설명할 필요 없이, 아래 6개 칸만 채우면 대부분의 위임 실패를 막는다.

영역채울 내용
Commands실제 실행할 커맨드와 플래그 (예: pytest -x tests/)
Testing어떤 프레임워크, 어디에 두는지, 어느 정도 커버해야 하는지
Project structure디렉터리 레이아웃 (파일이 어디로 가야 하는지)
Code style설명보다 실제 코드 샘플 1개가 더 정확하다
Git workflow브랜치명, 커밋 메시지 형식, PR 요건
Boundaries절대 하면 안 되는 것 (아래 3단계 표 참고)

주의할 것 하나 — Osmani는 이걸 "지시의 저주(curse of instructions)"라고 부르는데, 한 프롬프트에 요구사항이 쌓일수록 AI 성능이 떨어진다. 6개를 한 번에 다 쓰지 말고, 블록 단위로 필요한 만큼만 쓴다.

권한 3단계

✅ ALWAYS DO
승인 없이 진행. 예: 테스트 작성, 로컬 파일 수정, 로컬 실행
⚠️ ASK FIRST
영향이 크면 먼저 물어본다. 예: 새 의존성 추가, 스키마 변경, 클라우드 리소스 생성
🚫 NEVER DO
하드 스톱. 예: git push, 프로덕션 설정, 시크릿 파일 수정

이 3단계는 이미 이 세션의 CLAUDE.md 안전 규칙(파괴적 명령·git push·시크릿 파일)과 정확히 같은 구조다 — 새로 배울 게 아니라, 지금까지 무의식적으로 따라온 규칙에 이름을 붙인 것뿐이다.

03

Claude Code + Codex, 서로 다른 눈으로 검증하기

같은 모델이 자기가 쓴 코드를 스스로 검토하는 건 "자동수정이 자기 자동수정을 검토하는" 것과 같다. 서로 다른 벤더의 모델은 학습 과정이 다르기 때문에 놓치는 지점도 다르다 — 한쪽이 놓친 SQL 인젝션 패턴을 다른 쪽이 잡아내는 식이다. 이건 이미 사용자가 이전 프로젝트에서 codex exec(gpt-5.6-sol, high reasoning)로 Claude 산출물을 검증하던 습관인데, 이번 스프린트에서는 그 습관을 공식 파이프라인으로 승격한다.

Coordinator
사용자
스펙 작성, 최종 승인
Implementor
Claude Code
스펙대로 구현, 작은 diff 단위
Verifier
Codex
스펙과 대조 검증, 다른 결점 탐색
실행 리듬

프로젝트 전체를 몰아서 한 번에 검증하지 않는다. 레이어 하나(엔드포인트 1개, 스키마 1개, Dockerfile 1개)가 끝날 때마다 Codex 검증을 1회 돌린다 — Spec Kit의 "작은 diff" 원칙과 같은 이유다. 검증 범위가 좁을수록 결함이 명확하게 드러난다.

04

2일 스프린트

Day 1은 로컬에서 완전히 도는 것을 만든다. Day 2는 그걸 클라우드에 최소한으로 얹고 관측 가능하게 만든다. Kubernetes, Terraform, 재학습 파이프라인 자동화 같은 것들은 의도적으로 범위 밖에 둔다 — 개념만 한 줄로 짚고 넘어간다.

DAY 1

로컬에서 도는 것 만들기

모델 → API → 저장 → 컨테이너, 네 블록을 순서대로 스펙-구현-검증한다.

블록 1 · 예측 모델 재건

60–90분
목표
삭제된 features.py/train.py를 스펙만으로 다시 만들게 시킨다 — 이 블록 자체가 "제로베이스 위임" 연습
산출물
과거 EPL 매치 데이터를 받아 홈/원정 승무패 확률을 내는 학습된 모델 파일
검증
Codex에게 "데이터 누수(data leakage) 없는지"만 집중 검토 요청 — 이 유형 버그가 가장 흔하고 발견하기 어렵다

블록 2 · FastAPI 서빙

45–60분
목표
GET /health, POST /predict 두 엔드포인트 + pytest
산출물
모델을 로드해서 요청마다 예측을 반환하는 API 서버
검증
잘못된 입력(팀명 오타, 빈 값)을 넣었을 때 500이 아니라 400을 반환하는지

블록 3 · 예측 기록 저장

45–60분
목표
Postgres에 예측마다 model_version/data_version/schema_version 3열과 함께 저장 — Alembic 내부 구조는 몰라도 되고, "왜 이 3열이 처음부터 필요한지"만 알면 충분
산출물
predictions 테이블 + 저장 로직
검증
모델을 재학습해서 버전이 바뀌었을 때 과거 기록의 버전 값이 덮어써지지 않는지

블록 4 · Docker Compose로 묶기

30–45분
목표
API 컨테이너 + DB 컨테이너를 함께 띄운다
함정
DB 컨테이너가 "시작됨" ≠ "요청을 받을 준비됨". healthcheck 없이 depends_on만 쓰면 API가 DB보다 먼저 붙으려다 죽는다
검증
docker compose up 한 번으로 /health, /predict 실호출이 성공하는지
DAY 2

배포와 관측, 최소한으로

클라우드 벤더 명령어 암기가 아니라, 어느 클라우드에서든 통하는 패턴을 잡는다.

블록 1 · CI/CD 게이팅 개념

30–45분
목표
test → build → deploy 3단계가 순서대로 통과해야만 다음으로 넘어가는 파이프라인 구성
일반개념
정적 키 파일 대신 OIDC 토큰 교환으로 클라우드에 인증하는 방식(GCP Workload Identity Federation, AWS AssumeRoleWithWebIdentity, Azure Entra workload identity federation — 이름은 달라도 원리는 동일)
검증
테스트를 일부러 실패시켰을 때 배포 단계까지 가지 않고 멈추는지

블록 2 · 최소 클라우드 배포

45–60분
목표
서버리스 컨테이너 서비스 하나에 API를 올린다 (GCP Cloud Run급 — 특정 벤더 학습이 목적이 아니므로 이미 계정이 있는 곳을 사용)
스코프 아웃
Kubernetes/GKE, Terraform — 이번엔 콘솔/CLI로 직접 배포하고 개념만 한 줄로 짚는다
검증
배포된 URL로 /health가 응답하는지

블록 3 · 최소 관측/롤백

30–45분
목표
구조화 로그(요청 ID 포함) + 헬스체크 실패 시 어떻게 알아차릴지 + 이전 버전으로 되돌리는 절차를 문서 한 장으로 정리
검증
일부러 배포를 망가뜨린 뒤, 문서만 보고 롤백 절차를 따라갈 수 있는지

블록 4 · 회고

20–30분
목표
이틀간 쓴 스펙 중 결과가 좋았던 것과 다시 써야 했던 것을 나란히 놓고 비교
