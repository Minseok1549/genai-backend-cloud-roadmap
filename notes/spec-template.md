# 재사용 스펙 템플릿 — 6영역 체크리스트

`genai-backend-cloud-roadmap` 2일 스프린트(모델 서빙 → CI/CD → 클라우드 배포 →
관측/롤백)를 실제로 위임해보고 채운 버전. Addy Osmani의 6영역(Commands / Testing /
Project structure / Code style / Git workflow / Boundaries) 틀을 그대로 쓰되,
각 항목에 "왜 이게 실전에서 문제가 됐는지"를 이번 경험에서 가져와 적었다.

다음 프로젝트를 위임할 때 이 파일을 복사해서 빈칸을 채우는 용도로 쓴다.

---

## 1. Commands

**무엇을 적어야 하는가**: 테스트/빌드/실행을 어떤 명령어로 하는지, 그리고 —
이번에 배운 것 — **어느 환경에서** 실행하는지까지.

이번 스프린트에서 실제로 걸렸던 지점: "CI를 통과시켜라"는 목표만 있고 "GitHub
Actions로 할지, 로컬 `act`로 검증할지"가 없어서 실행 전에 되물어야 했다. 로컬
`pytest`가 `test_db.py`에서 실패하는 것도 코드 버그가 아니라 "DB 컨테이너가
`ports:` 매핑이 없어 호스트에서 못 붙는다"는, 명령어를 어디서 돌리느냐에 따라
정상/비정상이 갈리는 문제였다 — 이런 건 스펙에 "이 테스트는 A 환경에서만
통과한다"라고 한 줄 적어두면 매번 재확인할 필요가 없다.

**템플릿**:
- 테스트: `<명령어>` — 통과해야 하는 환경: `<로컬 / CI / 둘 다>`
- 빌드: `<명령어>`
- 로컬 실행: `<명령어>`
- 배포: `<명령어>` (있다면)

## 2. Testing

**무엇을 적어야 하는가**: 무엇을 테스트로 증명해야 완료로 인정하는지 — "된다"의
정의.

이번 스프린트의 검증 기준은 대부분 "실제로 살아있는 것에 curl을 날려서 확인"
수준이었고, 이게 잘 맞았다. 배포가 "명령어가 성공 종료했다"가 아니라 "실제
`/health`가 200을 준다"로 정의돼 있었기 때문에, `.gcloudignore` 버그나 `PORT`
불일치 같은 "배포는 됐지만 실제로는 안 뜬" 상태를 놓치지 않았다. 반대로 롤백
런북은 "문서를 썼다"가 아니라 "실제로 장애를 내고 그 문서만 보고 복구되는지"로
검증했을 때 비로소 신뢰할 수 있었다 — 문서가 검증 기준 없이 존재하기만 했다면
빠뜨린 명령어가 있어도 몰랐을 것이다.

**템플릿**:
- 완료 기준: `<추상적 "동작한다"가 아니라 구체적으로 무엇을 호출해서 무슨 응답을
  받아야 하는지>`
- 실패를 일부러 만들어서 검증해야 하는 것: `<있다면 무엇을 부수고 무엇이 일어나야
  정상인지>`

## 3. Project structure

**무엇을 적어야 하는가**: 생성되는 파일 중 무엇이 커밋되고 무엇이 안 되는지,
그리고 — 이번에 세 번 반복된 실수 — **"안 커밋되는 파일을 다른 어떤 도구가
필요로 하는가"**.

`.gitignore`로 뺀 `models/`, `data/raw/`가 (1) GitHub Actions 체크아웃에서 안
보임 → artifact 업/다운로드로 해결, (2) `gcloud run deploy --source .` 업로드에서
`.gitignore`를 기본으로 따라가서 안 보임 → `.gcloudignore`로 예외 처리, 이렇게
같은 "gitignore된 파일이 다른 도구의 컨텍스트에서도 안 보인다"는 문제가 이름만
다른 무시 파일(`.gitignore`/`.dockerignore`/`.gcloudignore`)마다 매번 새로
드러났다. 이건 예측 가능한 패턴이므로 스펙에 미리 적어두면 반복 디버깅을 줄일 수
있다.

**템플릿**:
- 커밋되는 것: `<...>`
- 커밋 안 되는(생성되는) 것: `<...>` — 이걸 필요로 하는 다른 컨텍스트가 있는가?
  (CI 체크아웃 / 컨테이너 빌드 컨텍스트 / 배포 업로드 등, 각각 자기만의 무시
  파일을 가질 수 있음을 명시)

## 4. Code style

이번 스프린트에서는 코드 스타일 자체가 마찰의 원인이었던 적은 없었다(Day 1
블록들은 기존 코드베이스가 없는 완전한 백지였고, 리뷰는 Codex/Opus가 스타일이
아니라 정확성 버그 — 커넥션 풀 스레드 안전성, `CREATE TABLE` 레이스 컨디션 —
를 잡았다). 다만 "새 파일을 처음부터 짤 때"는 기존 관례가 없어 매번 판단해야
했다는 점은 남는다.

**템플릿**:
- 참고할 기존 파일/관례: `<...>` (없으면 "이번이 최초"라고 명시해서, 위임받는
  쪽이 스타일 일관성을 스스로 만들어야 함을 알게 한다)
- 에러 처리 원칙: `<예: 외부 의존성 실패는 핵심 기능을 막지 않는다 — 이번
  스프린트에서 "DB 죽어도 예측은 계속", "외부 API 캐시 갱신 실패해도 기존 캐시로
  계속"이 반복된 원칙이었다>`

## 5. Git workflow

이번 스프린트는 블록 하나 끝날 때마다 커밋 + 푸시하는 흐름으로 진행했고, 별
문제 없었다(공개 리포라 매 커밋이 CI를 실제로 돌렸다는 것도 검증 신뢰도를
높였다). 다만 "의도적으로 깨뜨린 테스트/코드를 커밋했다가 되돌리는" 시나리오가
두 번 있었는데(CI 게이팅 검증, 런북 검증), 후자는 로컬에서만 바꾸고 절대 커밋하지
않는 쪽을 택했다 — 라이브 서비스에 영향을 주는 "의도적 장애"는 git 히스토리에도
남기지 않는 편이 더 안전하다는 판단.

**템플릿**:
- 커밋 단위: `<예: 블록/기능 단위로 1커밋, 완료 시 즉시 푸시>`
- 의도적 실패를 검증용으로 만들 때: `<커밋할지 말지 미리 정해둔다 — 이번엔
  "라이브에 영향 주는 것은 로컬에서만, 절대 커밋 안 함"이 원칙이었다>`

## 6. Boundaries

**이번 스프린트에서 가장 자주, 그리고 가장 뒤늦게(실행 도중에) 등장한 영역.**
로컬 스코프 블록에서는 이 항목이 비어 있어도 문제가 안 됐지만, 클라우드/공유
자원을 건드리는 블록마다 매번 실행을 멈추고 사람에게 물어야 했다(리포 공개
범위, GCP 프로젝트 선택, 결제 계정 연결, DB로 인한 추가 비용, 라이브 서비스에
의도적 장애 배포). 다음 프로젝트에서는 이 6개를 처음부터 스펙에 박아두면
실행 중 멈추는 횟수를 줄일 수 있다.

**템플릿 — 다음 항목은 클라우드/공유 자원을 다루는 프로젝트라면 처음부터
채워둘 것**:
- 비용 상한: `<예: 무료 티어를 벗어나는 리소스(Cloud SQL 등)는 사전 승인 필요>`
- 클라우드 계정/프로젝트 격리 원칙: `<예: 관련 없는 기존 프로젝트에 얹지 않고
  새로 분리 — 나중에 통째로 삭제하기 쉽게>`
- 외부 공개 범위: `<예: 리포 public/private, 배포된 엔드포인트 인증 필요 여부>`
- 파괴적이거나 되돌리기 어려운 행동: `<예: 라이브 서비스에 의도적 장애 배포,
  force-push, 프로덕션 데이터 변경 — 사전 승인 없이는 실행하지 않는다>`
- 자동 안전장치가 막았을 때의 대응: `<예: 우회하지 말고 즉시 사람에게 설명하고
  구체적 승인을 받는다 — "포괄적 자율 진행 승인"만으로는 이 종류의 행동을
  허가받은 것으로 간주하지 않는다>`

## 총평 — 언제 이 템플릿을 꽉 채우고, 언제 짧게 가도 되는가

- **로컬/개인 스코프 작업**(파일시스템 안에서 끝나는 것): Commands/Testing만
  명확하면 충분했다. Boundaries를 비워둬도 실행이 막히지 않았다.
- **공유 자원·비용·공개 범위가 걸린 작업**(클라우드 배포, 외부 리포, 결제 계정):
  Boundaries를 미리 채우지 않으면, 결국 실행 도중 같은 질문들을 하나씩 다시
  받게 된다 — "짧은 스펙 + 실시간 확인"도 나쁜 전략은 아니지만, 그럴 거라면
  스펙을 짧게 쓴 이유가 "몰라서"가 아니라 "의도적으로 실행 시점 판단에 맡긴다"
  여야 한다.
