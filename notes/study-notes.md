# 백엔드~클라우드 위임 스프린트 — 바이블 노트

이 문서는 "무엇을 만들었는지"가 아니라 "왜 그렇게 만들었는지"를 남기기 위한 것이다.
나중에 이 프로젝트를 남에게 설명하거나, 비슷한 걸 다시 만들 때 이 문서만 읽으면
각 블록에서 실제로 무슨 판단을 했는지 복원할 수 있어야 한다.

전체 흐름: Day 1은 로컬에서 완전히 도는 서비스를 만들고, Day 2는 그걸 클라우드에
최소한으로 얹고 관측 가능하게 만든다. Spec Kit(Specify→Plan→Tasks→Implement) 순서로
블록마다 위임하고, Codex(또는 Claude Opus)가 교차 검증한다.

## Day 1 · 블록 1 — 예측 모델 재건 (features.py / train.py)

**목표**: 지워진 특징 생성·학습 코드를 스펙만으로 다시 만들게 시켰다. 이 블록 자체가
"제로베이스 위임 연습" — 코드를 보여주지 않고 무엇을 해야 하는지만 설명해서 결과물을
받아내는 것.

**핵심 개념 — 시간순 분리(time-based split)**
일반적인 머신러닝에서는 데이터를 무작위로 섞어서 train/test를 나눈다. 그런데 축구
경기 예측처럼 "미래를 맞추는" 문제에서 무작위로 섞으면, 모델이 미래 경기 데이터를
보고 과거 경기를 맞추는 셈이 되어 실제보다 정확도가 부풀려진다(data leakage). 그래서
날짜 순서대로 앞부분은 학습, 뒷부분은 평가에 쓰도록 분리했다. 게다가 같은 킥오프
시각에 여러 경기가 열릴 수 있어서, 분리 경계가 그 경기들 중간을 가르지 않도록 명시적으로
확인하는 로직을 넣었다.

**핵심 개념 — 시즌 캐싱 전략의 이원화**
`fetch_data.py`는 완결된 시즌(2023~2025)과 진행 중인 시즌(2026)을 다르게 다룬다.
완결 시즌은 결과가 절대 바뀌지 않으니 한 번 받으면 영구히 캐시해서 다시 안 받는다.
진행 중인 시즌은 새 경기가 계속 끝나므로 캐시가 일정 시간(6시간)보다 오래되면
다시 받아온다. 이렇게 나눈 이유는 두 가지다 — football-data.org 무료 티어가
분당 10회로 제한돼 있어서 불필요한 재요청을 피해야 하고, `/predict`가 항상 최신
팀 폼(최근 성적)을 반영해야 하기 때문이다.

**검증**: 별도 pytest(`tests/test_features.py`)로 특징 생성 로직을, `train.py` 실행
결과(accuracy, log_loss가 다수결 베이스라인보다 나은지)로 모델 자체를 검증했다.

## Day 1 · 블록 2 — FastAPI 서빙 (api.py)

**목표**: 학습된 모델을 `/predict` 엔드포인트로 서빙.

**핵심 개념 — lifespan과 startup 시점의 무거운 작업**
FastAPI의 `lifespan` 콘텍스트 매니저 안에서 모델 파일을 딱 한 번 로드해서
`app.state`에 담아둔다. 요청마다 파일을 다시 읽으면 느리고, 전역 변수에 담으면
테스트할 때 앱 인스턴스를 여러 개 만들기 어려워진다. `lifespan`은 그 중간 지점 —
앱 생명주기에 묶이면서도 인스턴스별로 독립적이다.

**핵심 개념 — 동기 핸들러가 스레드풀에서 돈다**
FastAPI(정확히는 Starlette)는 `async def`가 아닌 일반 `def` 핸들러를 만나면 이걸
자동으로 anyio의 스레드풀(기본 약 40개 스레드)에 던져서 실행한다. 즉 `/predict`가
동기 함수로 짜여 있어도 여러 요청이 "동시에" 처리된다는 뜻이다. 이 사실이 나중에
블록 3에서 DB 커넥션 풀을 고를 때 결정적인 이유가 된다(아래 참고).

## Day 1 · 블록 3 — 예측 기록 저장 (db.py)

**목표**: 모든 예측을 Postgres에 남기되, `model_version`/`data_version`/`schema_version`을
같이 저장해서 나중에 "이 예측이 어느 모델·어느 데이터로 나왔는지" 추적 가능하게 한다.
검증 기준: 모델을 재학습해서 `model_version`이 바뀌어도, 이미 저장된 과거 예측
행의 버전 값은 절대 바뀌면 안 된다.

**핵심 개념 — INSERT-only 설계로 감사 기록을 구조적으로 보호**
UPDATE 문 자체를 코드에 두지 않았다. "과거 기록을 덮어쓰지 않는다"는 요구사항을
검증 로직(테스트)에만 맡기지 않고,애초에 덮어쓸 방법이 없게 설계한 것이다. 새 예측은
항상 새 행(INSERT)으로 남고, `id`는 `RETURNING id`로 그 자리에서 받는다(레이스 조건이
있는 `SELECT max(id)` 방식은 다른 동시 요청이 먼저 삽입한 행의 id를 가로챌 수 있어서
피했다).

**핵심 개념 — 커넥션 풀은 왜 `ThreadedConnectionPool`이어야 하는가**
psycopg2에는 `SimpleConnectionPool`과 `ThreadedConnectionPool` 두 종류가 있다.
공식 문서에 `SimpleConnectionPool`은 스레드 세이프하지 않다고 명시돼 있다. 블록 2에서
확인했듯 FastAPI의 동기 핸들러는 여러 스레드에서 동시에 실행되므로, 여러 요청이
동시에 같은 풀에서 커넥션을 꺼내 쓴다 — 이때 `SimpleConnectionPool`을 쓰면 내부
카운터 증가나 풀 딕셔너리 조작이 원자적이지 않아 레이스가 나고, 최악의 경우 커넥션
누수나 반납 시 `KeyError`가 날 수 있다. 실제로 코드 리뷰(Claude Opus)에서 이 문제가
지적됐고 `ThreadedConnectionPool`로 교체했다. 이 프로젝트에서 "동시성 버그는 이론이
아니라 실제로 일어난다"를 처음 체감한 지점이다.

**핵심 개념 — `CREATE TABLE IF NOT EXISTS`도 레이스가 난다**
클라우드에 배포하면 인스턴스(레플리카)가 여러 개 동시에 뜨는 경우가 흔하다. 이때
여러 인스턴스가 동시에 `init_schema()`를 실행하면, "테이블이 있는지 확인 → 없으면
생성" 사이에 다른 프로세스가 끼어들 수 있다. 실제로 5개 스레드로 재현해보니 예상과
다르게 테이블 자체의 충돌(`DuplicateTable`)이 아니라, `SERIAL` 컬럼이 암묵적으로
만드는 시퀀스 이름 충돌(`UniqueViolation`)이 났다. 이 경험에서 얻은 교훈: "이 예외
타입이 나겠지"라고 짐작하지 말고, 실패하면 일단 롤백한 뒤 "내가 원하던 최종 상태가
실제로 만들어졌는가"(`SELECT to_regclass('predictions')`)를 다시 확인하는 방식이
훨씬 견고하다. 특정 예외 하나만 잡는 코드는 실전에서 배신당하기 쉽다.

**핵심 개념 — DB가 죽어도 서비스는 안 죽어야 한다**
`lifespan`에서 DB 연결을 try/except로 감쌌다. DB 연결이 실패해도 앱 자체는 정상
기동하고, `app.state.db_pool = None`으로 표시해둔 뒤 `/predict`는 계속 응답하되
기록만 건너뛴다. 이렇게 안 했다면 DB 하나가 다운됐다고 예측 서비스 전체가 죽는
꼴이 된다 — "부가 기능(기록)의 장애가 핵심 기능(예측)까지 끌고 내려가면 안 된다"는
원칙을 코드로 구현한 것. 실제로 컨테이너를 내려서 이 동작을 확인했다.

**세 가지 버전 값의 의미**
- `model_version`: `train.py` 실행마다 발급되는 타임스탬프(마이크로초까지, 재시도·병렬
  실행 시 충돌 방지). "이 예측이 어느 학습 결과물로 나왔나."
- `data_version`: 예측 시점에 실제로 쓰인 경기 데이터의 최신 날짜. "이 예측이 어느
  시점까지의 데이터를 반영했나."
- `schema_version`: 테이블 구조 자체의 버전(현재 1, 코드 상수). "이 행이 어떤 스키마로
  쓰였나" — 나중에 테이블 구조가 바뀌어도 과거 행을 구분할 수 있게.

의도적으로 남겨둔 한계(Day 2 이후 스코프): `data_version`은 과거 데이터의 정정·백필을
반영하지 못하고, 모델이 "학습에 쓴" 데이터셋 자체에 대한 기록은 없다(서빙 시점 데이터만
기록). 이건 버그가 아니라 "지금 스코프에서는 안 한다"고 명시적으로 정한 설계 결정이다.

## Day 1 · 블록 4 — Docker Compose로 묶기

**목표**: API 컨테이너와 DB 컨테이너를 `docker compose up` 한 번으로 띄우고, 실제
`/health`·`/predict` 호출이 성공하는지 검증.

**핵심 개념 — "컨테이너가 떴다" ≠ "요청을 받을 준비가 됐다"**
Postgres 컨테이너는 프로세스가 시작된 직후에도 초기화 중이라 바로 연결을 받지
못하는 구간이 있다. 그냥 `depends_on: [db]`만 쓰면 Compose는 "컨테이너 프로세스가
시작됐는지"만 보고 `api`를 바로 띄운다. 그래서 `depends_on: condition: service_healthy`와
진짜 `pg_isready` 헬스체크를 같이 써서, "DB가 연결을 받을 수 있는 상태"가 된 뒤에만
`api`가 시작하도록 순서를 강제했다. 실제 로그에서 `db-1 Waiting` → `db-1 Healthy` →
`api-1 Starting` 순서로 찍히는 걸 확인했다.

**핵심 개념 — `.dockerignore`와 `.gitignore`는 서로 다른 목적**
`data/raw/`와 `models/`는 `.gitignore`에 있다(생성된 산출물이라 git에 안 올림). 하지만
Docker 이미지에는 학습된 모델과 캐시된 데이터를 그대로 구워 넣는 게 맞다(컨테이너
기동마다 재학습·재수집하면 느리고, 비밀키를 빌드 과정에 넣어야 해서 더 위험하다).
그래서 `Dockerfile`은 `COPY models/ models/`, `COPY data/ data/`로 이 디렉터리들을
명시적으로 포함시키고, `.dockerignore`는 이것과 별개로 "빌드 컨텍스트에서 뺄 것"
(가상환경, git 메타데이터, 테스트 코드 등)만 관리한다. 이 구분을 모르면 "gitignore에
있으니 당연히 이미지에도 없겠지"라고 착각하기 쉽다.

**핵심 개념 — 환경변수 우선순위**
Compose에서 서비스의 `environment:`는 같은 서비스의 `env_file:`보다 우선한다. 이걸
이용해서 `.env`의 `DATABASE_URL`(로컬 `localhost` 기준, 컨테이너 네트워크에선 무효)은
그대로 두고, `docker-compose.yml`의 `environment:`에서만 컨테이너 네트워크의 서비스
이름(`db`)을 가리키도록 덮어썼다. `FOOTBALL_DATA_API_KEY`는 덮어쓸 필요가 없으니
`.env`에서 그대로 흘러들어온다.

## Day 2 · 블록 1 — CI/CD 게이팅 개념

**목표**: test → build → deploy 3단계가 순서대로 통과해야만 다음 단계로 넘어가는
파이프라인. 검증 기준: 테스트를 일부러 실패시켰을 때 배포 단계까지 가지 않고 멈추는지.

**핵심 개념 — job 의존성(`needs:`)이 곧 게이트다**
GitHub Actions에서 `needs: test`라고 쓰면, `test` job이 실패했을 때 그 다음 job은
"실행됐다가 실패"하는 게 아니라 아예 스킵된다. 이번에 실제로 테스트 하나를 일부러
`assert False`로 깨뜨려서 push해봤더니, `test` job은 58초 만에 실패했고 `build`/`deploy`
job은 0초 만에(=한 줄도 안 돌고) 스킵 상태로 끝났다. 이게 "파이프라인 게이팅"의 실체 —
복잡한 승인 절차가 아니라, 그냥 "이전 job이 성공해야 다음 job의 실행 조건이 성립한다"는
단순한 의존성 그래프다.

**핵심 개념 — CI 환경은 로컬과 다른 "빈 방"에서 시작한다**
로컬에서는 `models/`, `data/raw/`가 이미 디스크에 있었지만, GitHub Actions 러너는
매번 깨끗한 체크아웃에서 시작한다. `.gitignore`로 이 디렉터리들을 리포에서 뺐기
때문에, CI의 `build` job에서 그냥 `docker build`만 하면 `COPY models/ models/`가
실패한다. 이걸 어떻게 메울지가 실제 설계 결정이었다 — 두 옵션(① CI가 매번 실제
데이터로 재학습, ② 모델/데이터 파일 자체를 git에 커밋) 중 ①을 골랐다. 이유는
"매 커밋마다 최신 데이터로 재현 가능한 빌드"가 실제 서비스 운영 방식에 더 가깝고,
생성 파일을 버전 관리에 넣으면 파일 버전 관리가 이원화되기 때문이다. 대신 `test`
job에서 fetch+train을 한 번만 하고, 그 결과물을 `actions/upload-artifact`로
`build` job에 넘겨서 API 호출을 중복하지 않도록 했다(무료 티어 분당 10회 제한 고려).

**핵심 개념 — 시크릿은 코드에 안 들어간다**
`FOOTBALL_DATA_API_KEY`는 워크플로 파일(`.github/workflows/ci.yml`)에 값이 아니라
`${{ secrets.FOOTBALL_DATA_API_KEY }}`라는 참조만 적히고, 실제 값은 `gh secret set`으로
리포 설정에 별도 등록했다. 리포는 public이지만 시크릿 값 자체는 워크플로 로그에도
마스킹되어 노출되지 않는다.

**개념만 짚고 넘어간 것 — OIDC 토큰 교환**
지금 `deploy` job은 아직 placeholder라 실제 클라우드 인증이 필요 없다. 하지만
Day 2 블록 2에서 실제 배포를 붙이면 클라우드 자격증명이 필요해진다. 이때 정적 키
파일(예: 서비스 계정 JSON을 시크릿으로 박아두는 방식)보다 권장되는 방식이 OIDC
토큰 교환이다 — GitHub Actions가 매 실행마다 짧게 사는 ID 토큰을 발급받고, 클라우드
쪽에서 "이 토큰이 이 리포·이 브랜치에서 왔다"는 걸 검증해서 임시 자격증명을 내주는
방식. 이름은 벤더마다 다르다(GCP Workload Identity Federation, AWS
`AssumeRoleWithWebIdentity`, Azure Entra workload identity federation) 원리는
동일 — "장기 유효한 비밀키를 어딘가에 저장해두지 않아도 된다"는 것.

## Day 2 · 블록 2 — 최소 클라우드 배포

**목표**: 서버리스 컨테이너 서비스(GCP Cloud Run급) 하나에 API를 올린다. Kubernetes/GKE,
Terraform은 이번엔 의도적으로 스코프 아웃 — 콘솔/CLI로 직접 배포하고 개념만 짚는다.
검증 기준: 배포된 URL로 `/health`가 응답하는지.

**설계 결정 — 스프린트 전용 GCP 프로젝트 분리**
`gcloud`가 이미 다른 프로젝트(`stock-assistant-2026`)에 인증돼 있었지만, 그대로 쓰면
서로 무관한 두 스프린트의 클라우드 리소스가 한 프로젝트에 섞인다. 그래서 이 스프린트
전용 프로젝트(`genai-backend-cloud-roadmap`)를 새로 만들고 결제 계정을 연결했다.
"일단 되는 곳에 배포"보다 "나중에 통째로 지울 수 있는 경계"를 먼저 만든 것 — 클라우드
리소스는 로컬 파일과 달리 방치하면 계속 돈이 나가고, 프로젝트 단위로 지우는 게 개별
리소스를 하나씩 추적해서 지우는 것보다 훨씬 안전하다.

**설계 결정 — 지금은 DB 없이 배포**
Block 2의 검증 기준은 순수하게 `/health` 응답이지 예측 기록 저장이 아니다. 관리형
Postgres(Cloud SQL)는 무료 티어가 없어 상시 비용(월 $7~15선)이 발생하는데, 이 블록의
스코프를 넘어서는 지출이다. 그래서 `DATABASE_URL` 환경변수 없이 배포했고, Day 1
블록 3에서 이미 만들어둔 graceful degradation(DB 연결 실패해도 앱은 정상 기동,
`/predict`는 계속 응답하되 기록만 건너뜀) 덕분에 `/health`·`/predict` 둘 다 문제없이
동작했다. "이 블록에서 필요한 것"과 "이 서비스가 결국 필요로 할 것"을 구분해서, 후자를
미리 당겨오지 않은 사례.

**막혔던 문제 1 — `gcloud`가 `.gitignore`를 그대로 따라간다**
`gcloud run deploy --source .`로 배포하면, 소스를 압축해서 Cloud Build로 올리는데
이때 `.gcloudignore`가 없으면 `.gitignore`의 규칙을 기본값으로 그대로 쓴다. 그런데
`models/`와 `data/raw/`는 정확히 `.gitignore`에 있는 디렉터리였다 — 로컬 디스크에는
파일이 멀쩡히 있는데도 업로드에서 통째로 빠져서 `COPY models/ models/`가 "그런 경로
없음"으로 실패했다. `.dockerignore` 때 이미 한 번 겪었던 "제외 규칙 파일마다 목적이
다르다"는 교훈이 `.gcloudignore`에서도 그대로 반복된 것 — 이번엔 명시적으로
`.gcloudignore`를 만들어서 두 디렉터리를 무시 목록에서 뺐다.

**막혔던 문제 2 — Cloud Run은 `$PORT`를 기대하는데 Dockerfile은 8000을 하드코딩**
빌드는 성공했는데 배포가 "컨테이너가 포트를 안 열었다"며 실패했다. Cloud Run은 컨테이너
기동 시 `PORT` 환경변수(기본값 8080)를 주입하고, 그 포트로 TCP 헬스체크를 한다. 그런데
`CMD ["uvicorn", ..., "--port", "8000"]`는 그 값을 무시하고 무조건 8000에서만 리슨했다.
로그(`gcloud logging read`)로 "uvicorn은 8000에서 떴는데 프로브는 8080을 두드리고
있다"는 걸 직접 확인한 뒤, `CMD`를 셸 형식으로 바꿔서 `${PORT}`를 런타임에 읽게
고쳤다(`ENV PORT=8000`으로 로컬/Compose 기본값은 유지). 이 수정 하나로 로컬
Docker Compose 동작과 Cloud Run 동작이 동시에 성립한다 — "플랫폼이 주입하는 값을
읽되, 안 주면 합리적인 기본값을 쓴다"는 패턴.

**검증**: `gcloud run deploy`가 준 실제 URL(`https://epl-predictor-*.run.app`)에
직접 `curl`로 `/health`(200), `/predict`(200, 실제 확률값)를 확인했다. 로컬
`TestClient`나 Docker Compose가 아니라, 인터넷 건너 진짜 배포된 서비스를 두드린
결과라는 점이 이 검증의 핵심이다.

## Day 2 · 블록 3 — 최소 관측/롤백

**목표**: 구조화 로그(요청 ID 포함) + 헬스체크 실패 시 어떻게 알아차릴지 + 이전 버전으로
되돌리는 절차를 문서 한 장(런북)으로 정리. 검증 기준: 일부러 배포를 망가뜨린 뒤,
그 문서만 보고 롤백 절차를 따라갈 수 있는지.

**핵심 개념 — 구조화 로그는 "포맷"의 문제이지 새 인프라가 아니다**
별도 로깅 SDK나 에이전트를 깔지 않았다. 컨테이너가 stdout에 한 줄짜리 JSON을
찍기만 하면, Cloud Run(같은 원리로 AWS의 CloudWatch Logs, Azure의 Log Analytics도)이
그 컨테이너의 표준출력을 자동으로 수집해서 JSON을 파싱해준다. 실제로
`gcloud logging read`에 `jsonPayload.message="request completed"` 같은 조건을
걸어서 필드 단위로 검색되는 걸 확인했다 — "구조화 로그"란 결국 "로그 한 줄이
사람이 아니라 기계가 파싱하기 쉬운 형태(JSON)로 되어 있다"는 것뿐이다.

**핵심 개념 — 요청 ID로 로그를 "한 요청" 단위로 묶는다**
동시에 여러 요청이 처리되는 서비스에서, 로그가 시간순으로만 섞여 있으면 "이 에러가
어느 요청 때문에 났는지" 알기 어렵다. 미들웨어에서 요청마다 ID를 하나 발급(또는
호출자가 이미 붙여왔으면 그대로 승계)해서, 그 요청과 관련된 모든 로그 줄에 같은
`request_id`를 심었다. 응답 헤더(`X-Request-ID`)에도 그대로 실어 보내므로, 사용자가
"이 요청이 이상해요"라고 신고하면 그 헤더값 하나로 서버 로그에서 관련 줄을 전부
찾을 수 있다 — 분산 추적(distributed tracing)의 가장 축소된 형태.

**핵심 개념 — 트래픽 롤백은 "재배포"가 아니라 "트래픽 스위치"다**
Cloud Run은 리비전(revision)이라는 불변 스냅샷 여러 개를 동시에 보관하고, 트래픽을
퍼센트 단위로 특정 리비전에 라우팅한다. 그래서 "롤백"은 새 코드를 다시 빌드해서
배포하는 게 아니라, 이미 존재하는 이전 리비전으로 트래픽 100%를 되돌리는 것뿐이다
(`gcloud run services update-traffic --to-revisions=<리비전>=100`). 이게 빠른 이유는
빌드가 필요 없기 때문 — 컨테이너 이미지는 이미 만들어져 있고, 그냥 로드밸런서
설정만 바뀐다. 실제로 실행해보니 이 스위치 자체는 몇 초 안에 끝났다.

**검증 — 실제로 장애를 내고 문서만 보고 복구**
`/health`가 500을 던지도록 코드를 바꿔서 실제로 배포했고(사용자 승인 하에 진행 —
자동 모드 안전장치가 "의도적으로 깨진 코드를 라이브 서비스에 배포"하는 걸 위험
행동으로 분류해 한 번 막았던 걸, 개인 연습용 프로젝트이고 실사용자 영향이 없다는
점을 설명하고 명시적 승인을 받아 진행함), `curl`로 500을 직접 확인한 뒤, 이 세션의
기억이나 맥락을 참고하지 않고 오직 `notes/runbook.md`에 적힌 명령어만 그대로 복붙
실행해서 리비전 목록 확인 → 트래픽 전환 → 복구 확인까지 끝냈다. 200으로 돌아오는 걸
확인한 뒤 로컬 코드는 즉시 원상복구했다(애초에 커밋되지 않은 임시 변경이라 git
히스토리에는 남지 않음).

**의도적으로 스코프 아웃한 것 — 자동 알림(alerting)**
지금은 "사람이 `curl`로 확인"하는 수동 절차다. 진짜 프로덕션이라면 Cloud Monitoring
Uptime Check + Alerting Policy(또는 AWS Route 53 Health Check + CloudWatch Alarm,
Azure Application Insights 가용성 테스트)를 붙여서 장애를 사람이 알아차리기 전에
시스템이 먼저 알려줘야 한다. 런북 문서에 이걸 개념으로 명시했지만 구현하지는
않았다 — 이번 스프린트의 "최소" 스코프를 넘는 판단.

## Day 2 · 블록 4 — 회고

**목표**: 이틀간 쓴 스펙 중 결과가 좋았던 것과 다시 써야 했던 것을 나란히 놓고 비교.
산출물: 6영역 체크리스트를 이번 경험으로 다시 채운 재사용 템플릿(→ `notes/spec-template.md`).

**관찰 1 — Day 1(로컬 스코프)은 매끄러웠고, Day 2(공유·클라우드 스코프)는 매 블록마다
실시간 확인이 필요했다**

Day 1의 블록 스펙(목표/산출물/검증, 3줄 남짓)은 그대로 위임해도 별문제 없이 진행됐다.
문제가 났던 지점은 전부 "구현 디테일"이었지(커넥션 풀 종류, 예외 처리 방식) "이걸
해도 되는지"를 사용자에게 되물어야 하는 지점은 없었다. 반면 Day 2는 블록마다
최소 한 번씩 `AskUserQuestion`으로 멈춰야 했다:

| 블록 | 되물어야 했던 것 | 6영역 중 빠져있던 것 |
|---|---|---|
| 블록 1 (CI 게이팅) | CI를 어디서 실행할지(GitHub Actions vs 로컬 act) | Commands/Project structure |
| 블록 1 | 리포를 public/private 중 뭘로 할지 | Boundaries |
| 블록 1 | CI에서 모델/데이터를 어떻게 확보할지 | Project structure |
| 블록 2 (클라우드 배포) | 어느 GCP 프로젝트에 배포할지 | Boundaries |
| 블록 2 | 결제 계정을 연결해도 되는지 | Boundaries |
| 블록 2 | DB(Cloud SQL)까지 배포할지, 비용을 감수할지 | Boundaries |
| 블록 3 (관측/롤백) | 롤백 검증을 위해 라이브 서비스에 실제 장애를 배포해도 되는지 | Boundaries |

**결론**: 스펙이 "다시 써야 했던" 게 아니라 — 애초에 Day 2 블록 스펙들은 로컬
스코프였던 Day 1과 똑같은 서술 길이(목표/스코프아웃/검증 3줄)를 유지했는데, 그
서술 길이가 감당할 수 있는 범위를 스코프 자체가 넘어섰다. "결제가 발생하는지",
"외부에 공개되는지", "실제 서비스에 영향을 주는지" 같은 질문은 로컬 블록에서는
아예 존재하지 않는 축이었는데, 클라우드 블록에서는 매번 등장했다. 즉 **Boundaries
칸이 비어 있어도 괜찮은 스코프(로컬)와, Boundaries 칸이 없으면 반드시 실행이
멈추는 스코프(공유 자원·비용·공개 범위가 걸린 곳)가 따로 있다** — 이게 이번
이틀에서 가장 재사용 가치가 큰 교훈이다.

**관찰 2 — 짧은 스펙이 "틀린" 게 아니라, 짧은 스펙은 실행 중 질문을 예산으로 잡아야
한다**

Osmani의 "지시의 저주" 원칙(한 프롬프트에 요구사항을 다 욱여넣지 말 것)은 이번에도
유효했다 — Day 2 블록 스펙을 처음부터 "GCP 프로젝트는 새로 파고, 리포는 public이고,
DB는 비용 때문에 나중에 붙이고, 장애 재현은 사전 승인받고" 식으로 전부 미리
적었다면 오히려 각 결정의 맥락(왜 그런지)이 실행 시점의 실제 상태와 안 맞았을 수도
있다(예: gcloud가 이미 다른 프로젝트에 물려있었다는 건 실행해보기 전엔 몰랐다).
**짧은 스펙 + 실행 중 실시간 확인**이 **긴 스펙 한 방**보다 클라우드처럼 "실행 전엔
알 수 없는 현재 상태"가 많은 도메인에서는 오히려 더 정확했다. 다만 이건 "질문이
안 나오게 스펙을 완벽히 쓰자"가 목표가 되면 안 된다는 뜻이지, 질문 자체를 줄이자는
뜻은 아니다.

**관찰 3 — 자동 안전장치가 한 번 막아준 것도 "스펙이 부족했다"의 일종**

블록 3에서 "라이브 서비스에 의도적 장애를 배포"하는 행동을 자동 모드 분류기가
막았다. 이건 Boundaries 영역에 "파괴적이거나 되돌리기 어려운 행동은 사전 승인
필요"라는 항목이 애초에 없었기 때문에 실행 시점에야 드러난 경계선이다 — 사람이
쓰는 스펙이든 자동 분류기든, "이건 명시적으로 안 물어봤다"는 지점에서는 결국
멈추고 확인하게 되어 있다는 걸 보여준 사례.

## 운영 확장 — 매일 자동 추적/예측 (Day 2 이후)

**목표**: 지금까지는 "누가 호출하면 그 순간 예측"하는 구조였다. 이걸 실제
운영 서비스답게 "매일 그날 예정된 EPL 경기를 자동으로 찾아 예측하고 기록"하는
파이프라인으로 확장한다.

**아키텍처 결정 — 왜 Cloud SQL이 아니라 GCS + Cloud Run Job인가**

매일 쌓이는 예측 기록을 저장할 곳이 필요한데, 이미 Block 2에서 "DB는 비용 때문에
보류"라고 결정한 바 있다. 이번엔 실제로 매일 뭔가를 저장해야 하므로 이 결정을
다시 마주했는데, Cloud SQL(가장 작은 인스턴스도 상시 과금) 대신 **GCS 버킷에
JSON 파일을 쌓는** 방식을 택했다 — 이 프로젝트 규모(하루 최대 십여 건의 작은
JSON)에서는 GCS 무료 티어 안에서 사실상 영구히 해결된다. 상시 떠 있는 서버가
필요 없다는 것도 중요한 차이: Cloud Run **Service**(요청이 오면 응답하는 상시
컨테이너)가 아니라 Cloud Run **Job**(트리거되면 한 번 실행하고 끝나는 배치)을
썼다 — 하루 한 번 몇 초 도는 작업에 상시 서비스를 쓸 이유가 없다.

**아키텍처**: Cloud Scheduler(매일 06:00 UTC) → Cloud Run Job 트리거 → 그날
UTC 날짜에 예정된 경기 조회(`data.load_fixtures_on_date`) → 기존 모델로 예측
(`predictor.predict_match`) → 결과를 GCS에 `predictions/YYYY-MM-DD.json`으로 저장.

**코드 공유 리팩터링**: `/predict` 엔드포인트(api.py)와 이 배치 작업
(daily_predict.py)이 "팀명 검증 → 폼 계산 → 모델 추론"이라는 같은 로직을 쓴다.
이 로직을 그대로 각자 구현하면 나중에 한쪽만 고치고 다른 쪽을 안 고치는 식으로
어긋날 수 있어서, `predictor.py`(예측 로직)와 `logutil.py`(구조화 로그)를 공용
모듈로 뽑아 두 진입점이 같은 함수를 호출하게 만들었다. "결과가 저장되는 곳만
다를 뿐, 예측 자체는 API로 직접 물어봤을 때와 절대 갈라지지 않는다"는 게 이
리팩터링의 목적.

**실제로 겪은 에러 — Cloud Run Jobs를 v1 API로 트리거하려다 403**: Cloud
Scheduler가 Cloud Run Job을 트리거하는 표준 URI 패턴을 처음에
`https://{region}-run.googleapis.com/apis/run.googleapis.com/v1/namespaces/{project}/jobs/{job}:run`
(리전별 v1 네임스페이스 API, Cloud Run **Service**용 레거시 Knative 경로)로
잡았는데, 실행할 때마다 403이 났다. Cloud Run **Job**은 v2 전용 리소스라 v1
API가 애초에 이 리소스를 인식하지 못한 것 — IAM 권한 문제가 아니라 잘못된
API 버전 경로 문제였다. `https://run.googleapis.com/v2/projects/{project}/locations/{region}/jobs/{job}:run`
(전역 엔드포인트, v2 API)로 바꾸니 200으로 정상 트리거됐다. **교훈**: 인증
오류(403/401)가 나면 권한부터 의심하기 쉬운데, 리소스 버전(v1 vs v2)이 애초에
안 맞아서 나는 403도 있다 — 로그의 실제 응답 코드와 사용한 API 문서 버전을
먼저 맞춰보는 게 IAM 바인딩을 계속 고치는 것보다 빠를 때가 있다.

**검증**: 로컬에서 오늘 실제 5경기(콤바인 승격팀 2팀은 폼 부족으로 자동 스킵,
로그로 기록)를 예측 → Cloud Run Job으로 실제 배포 → `gcloud run jobs execute`로
수동 실행해 GCS에 실제 파일이 쌓이는 것 확인 → **Cloud Scheduler의 "실행" 버튼을
직접 눌러 스케줄러 → Job → GCS 전체 경로**가 (수동 execute가 아니라) 스케줄러
트리거 경로로도 동작하는 것까지 확인. 매일 06:00 UTC 자동 실행은 다음 스케줄
때 그대로 검증된다.
